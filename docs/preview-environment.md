# بيئة المعاينة — قاعدة بيانات منفصلة لنشرات الـ PR

## لماذا وُجدت

نشرات المعاينة في Vercel (كل PR) كانت **تفشل دائماً** بينما الإنتاج ينجح:
متغيّرات البيئة مضبوطة في Environment = Production وحدها. و
[`lib/supabase-server.ts`](../lib/supabase-server.ts) يُنشئ العميل لحظة تحميل
الوحدة ويرمي خطأً إن غاب المتغيّر، و`next build` يحمّل كل مسار ليجمع بياناته —
فيسقط البناء كله بـ:

```
Error: Failed to collect page data for /api/conversations/[id]/bot
  [cause]: متغيّر البيئة NEXT_PUBLIC_SUPABASE_URL غير مضبوط…
```

**ولماذا قاعدة منفصلة لا مفاتيح الإنتاج:** مفتاح `service_role` يتجاوز RLS.
وضعه في بيئة المعاينة يعني أن كل فرع قيد المراجعة يحصل على نشرة حيّة تكتب في
بيانات التجار والشحنات الحقيقية — والشحنات تُعامل معاملة الأنظمة المالية
الحساسة (بند ٤ في `CLAUDE.md`).

## المتغيّرات المطلوبة في Vercel → Environment Variables → **Preview**

```
NEXT_PUBLIC_SUPABASE_URL=https://bytmivugrmzdiqdxtbrd.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=<مفتاح anon من لوحة bariq-preview>
SUPABASE_SERVICE_ROLE_KEY=<مفتاح service_role من لوحة bariq-preview>
```

يُضافان من: Supabase Dashboard → bariq-preview → Project Settings → API Keys.

⚠️ لا تُنسخ مفاتيح الإنتاج إلى Preview بحال — ذلك يُبطل الغرض من هذا المشروع
كله.

الأسرار الأخرى (`BARIQ_BOT_WEBHOOK_SECRET`, `BARIQ_DELIVERY_SYNC_SECRET`,
`N8N_WEBHOOK_URL`) ليست شرطاً لنجاح البناء: مساراتها تفشل فشلاً مغلقاً بـ ٥٠٣
إن غابت، وهو السلوك المقصود. تُضاف بقيم اختبارية إن أردت تجربة تلك المسارات في
المعاينة — ولا تُنسخ قيم الإنتاج.

## كيف بُنيت القاعدة (وما اكتُشف أثناء ذلك)

⚠️ **سلسلة الترحيلات ليست قابلة للتطبيق بترتيبها الرقمي على قاعدة جديدة.**
ثلاثة كسور مرصودة:

1. **الترحيل ٠٠٢ يسبق ٠١٠ وهو يحتاجه:** `shipments.order_id` يشير إلى
   `public.orders` الذي يُنشئه الترحيل ٠١٠. فالترتيب الصحيح للتطبيق هو:
   `002` (التجار والمندوبون) → `010` (بقية الجداول) → `002` (الشحنات).

2. **جدولا `conversations` و`messages`** كانا يُفهرسان ويُؤمَّنان في الترحيل
   ٠٠٣ دون أن يُنشئهما أي ترحيل — نشآ في القاعدة الحية خارج المستودع.
   **أُصلح:** أُضيف تعريفهما إلى الترحيل ٠٠٣ نفسه.

3. **خمسة أعمدة في الإنتاج لا ينشئها أي ترحيل**، أربعة منها يقرؤها ويكتبها
   `app/api/merchants/route.ts` — أي أن لوحة التجار تنهار على أي قاعدة تُبنى
   من هذا المستودع. **أُصلح:** الترحيل
   [`017`](../supabase/migrations/017_document_merchant_profile_drift.sql).

وما استُثني عمداً عند بناء قاعدة المعاينة:

| المُستثنى | السبب |
|---|---|
| الترحيل ٠٠٨ كاملاً | جسر n8n: محفّز على `conversation_log` (جدول حقبة n8n لا ينشئه أي ترحيل ولا يقرؤه تطبيق Next.js) |
| الترحيل ٠٠٩ كاملاً | جسره نفسه؛ وأجزاؤه التي تخصّ التطبيق (`orders.order_content` وفهارس الهاتف) مضمّنة سلفاً في الترحيل ٠١٠ |
| القسم ٨ من الترحيل ٠٠٣ | ترحيل بيانات تاريخية من `conversation_log` — لا بيانات قديمة في بيئة جديدة |
| الترحيل ٠١٥ | إصلاح صفوف `auth.users` مُنشأة يدوياً — لا وجود لها هنا |

ثم شُغِّل [`supabase/seed/002_plans_catalog.sql`](../supabase/seed/002_plans_catalog.sql)
لزرع الباقات الخمس — بدونها يفشل التسجيل الذاتي بـ «باقة البداية المجانية غير
مُهيَّأة».

## التحقق المُنفَّذ

- **تطابق المخطط:** قورنت بصمة أعمدة الجداول الخمسة والعشرين التي يستعملها
  التطبيق (`md5` لتجميع `column_name/data_type`) بين الإنتاج والمعاينة —
  **٢٥/٢٥ متطابقة**.
- **اختبار وظيفي:** تاجر + اشتراك Spark + إدراج منتج نجح؛ وإدراج لتاجر بلا
  اشتراك رُفض بـ `BQ002` من `enforce_plan_limit` كما يجب. نُظّفت بيانات
  الاختبار بعدها (`merchants = 0`).

## إعادة بناء بيئة مماثلة

طبّق بالترتيب: `002` (الأقسام ١–٢) → `010` (الأقسام ١–٧) → `002` (الأقسام
٣–٧) → `010` (٨–٩) → `001` → `003` (بلا القسم ٨) → `004`–`007` → `011`–`014`
→ `016` → `017`، ثم `seed/002_plans_catalog.sql`.

المالك يُمنح دوره تلقائياً عند أول دخول — لا يلزم تشغيل
`seed/001_bootstrap_platform_owner.sql` (انظر
[`lib/platform-owner.ts`](../lib/platform-owner.ts)).
